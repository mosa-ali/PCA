## Decision classification rule

Open decisions are visible and classified: **PRE-IMPLEMENTATION BLOCKER** must be approved before its named phase; **PRODUCT DEFAULT DECISION** may remain proposed at A-100 when alternatives, recommendation and phase are specified; **EXTERNAL DEPENDENCY** has a fallback; **A-100 BLOCKER** means architecture cannot be safely specified without a ruling.

## Residual risks

| Risk | Impact | Mitigation / gate |
|---|---|---|
| Android authority, OEM background limits, VPN disable | High | capability matrix, health/degraded state, Standard fallback; validate PCA-2/17. |
| Apple entitlement / opaque activity model | High | entitlement application, explicit fallback and capability labels; validate PCA-15/17. |
| Stolen/offline device or recovery-code theft | High | signed epoch rotation, recovery authentication, stale/revoked state; no retroactive wipe claim. |
| E2EE support/recovery complexity | High | recovery envelope, replacement-device procedure, no support decryption; test PCA-1/17. |
| Classifier error or malicious rules/models | Medium | deterministic precedence, signing, rollback and appeal path. |
| Platform/policy/source changes | High | doc 33 180-day source revalidation before each affected phase. |
| Architecture status documents drifting from actual implementation state | Medium | Repository survey conducted 2026-08-14 (`PCA-DOC-REALIGN-1`) found `docs/architecture/30_IMPLEMENTATION_PROGRAMME.md`, `PCA_ARCHITECTURE_MASTER_v1.0.md`, `docs/architecture/README.md`, `MANIFEST.md`, and `34_ARCHITECTURE_COMPLETION_GATE.md` all still asserting `IMPLEMENTATION_STATUS = NOT_STARTED` despite substantial source (~33,000 lines Android, ~16,800 lines backend, ~10,600 lines Parent Web) already existing. Mitigated for this pass by realignment to the `SOURCE_COMPLETE`/`VALIDATED_COMPLETE`/`PRODUCTION_READY` framework (doc 00 Section 8A); ongoing mitigation requires updating doc 30/32 status alongside code changes rather than only at periodic realignment passes — this is a process discipline gap, not a one-time fix. |
| Device-slot concurrency race (two simultaneous enrollment attempts consuming the same last entitlement slot) — Addendum 002 Section 8 | High | Mandatory atomic reserve-if-under-limit operation (`PCA-ADD-PA-038`) and a release-blocking concurrent-reservation race test (`PCA-ADD-PA-039`); no count-then-insert pattern permitted. Validate in PCA-PA-2 (Addendum 002). |
| Payment/webhook forgery, replay, or double-application of an entitlement increase — Addendum 002 Sections 13, 8.1 | High | Provider signature verification, idempotency keyed to provider event ID, replay/freshness checks, server-side status authority over client redirects (`PCA-ADD-BILL-030`–`035`, `PCA-ADD-BILL-046`). Validate in PCA-BILL-2/PCA-PA-5 (Addendum 002). |
| Payment secret mishandling (raw card/bank data, unredacted provider secrets) — Addendum 002 Section 11 | High | No-raw-PAN/CVV/bank-credential storage, provider-hosted/tokenized checkout only, secrets-manager-only credential storage, privacy-absence testing extended to the Billing domain (`PCA-ADD-BILL-023`–`026`). Validate in PCA-BILL-2/PCA-PA-5 (Addendum 002). |
| Platform-admin authority silently collapsing into family RBAC or a bare `isAdmin` flag — Addendum 002 Section 4 | High | Mandatory separate account type, session type, RBAC, MFA, step-up, and audit for every Platform Administration role; `isAdmin=true`-style flags on a family account explicitly rejected as sufficient authority (`PCA-ADD-PA-010`–`020`). Validate in PCA-PA-1 (Addendum 002). |
