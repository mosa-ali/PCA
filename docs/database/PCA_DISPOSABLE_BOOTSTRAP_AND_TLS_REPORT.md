## 3. F-1 — database TLS now fails closed

### What was actually wrong, confirmed from mysql2's source

`ConnectionConfig` resolves `this.ssl = typeof options.ssl === 'string' ?
getSSLProfile(options.ssl) : options.ssl || false`. An absent `ssl` option is
therefore exactly `false` — a plaintext connection carrying the database
password and every family record. `getPool()` passed only a URI.

Measured against real MySQL 8.4.11:

| Connection string | Result |
|---|---|
| `mysql://…/db` | `ssl=false`, `Ssl_cipher` empty — **plaintext** |
| `mysql://…/db?ssl={"rejectUnauthorized":true}` | TLS |
| `mysql://…/db?ssl-mode=REQUIRED` | **ignored** with a stderr warning — **plaintext** |

The third is the standard MySQL client spelling and it fails **open**.

### The fix

`PCA_DATABASE_TLS` must now be stated, never inferred:

- `REQUIRED` → TLS 1.2+, `rejectUnauthorized: true`, optional
  `PCA_DATABASE_TLS_CA` (inline PEM or file path; unreadable = hard error, never
  a silent fall back to system trust).
- `DISABLED` → plaintext, **refused in a production-sensitive runtime**.
- unset → plaintext in test/development; **hard error** in production-sensitive.
- anything else → hard error, always.

There is deliberately **no "encrypt but skip verification" mode**: an unverified
session authenticates nothing. A private CA is supported the honest way instead.

Checked at **boot** (`assertDatabaseTlsConfiguration()` in `main.ts`), not at
first query — the same posture the email configuration now takes.

### Proof, against real servers

Against the plaintext Compose container:

```
plaintext posture              -> Ssl_cipher "" (genuinely unencrypted)
REQUIRED against untrusted cert -> HANDSHAKE_SSL_ERROR (fails closed, no downgrade)
REQUIRED + smuggled ?ssl={"rejectUnauthorized":false} in the URL
                               -> still fails closed
   control: without the explicit posture that same URL DOES establish TLS,
   so the assertion proves the explicit option won, not that the URL was inert
```

Against a purpose-built MySQL 8.4.11 with `require_secure_transport=ON` and a
properly issued certificate (SAN `IP:127.0.0.1`):

```
A. plaintext                     -> ER_SECURE_TRANSPORT_REQUIRED (server refuses)
B. REQUIRED, no CA               -> fails closed (private CA not in system trust)
C. REQUIRED + PCA_DATABASE_TLS_CA-> CONNECTED  TLSv1.3  TLS_AES_256_GCM_SHA384
                                    server 8.4.11, require_secure_transport=1
```

That temporary server and its image were removed afterwards.

`12/12` tests, of which three open real connections.

**Azure confirmation that the live connection is encrypted remains
`NOT_TESTED`** — it requires the 8.4 server and credentials.

## 4. Azure preflight allowlist — narrowed, not removed

`verify-mysql.mjs` **creates schema**, so its hostname allowlist is a real
control. It previously accepted only `127.0.0.1`/`localhost`/`mysql`, which also
made an authorized remote disposable database unreachable.

The allowlist was **not removed and no hostname was hardcoded**. A remote target
must be declared twice, deliberately, and carry TLS — three independent keys, so
no single typo widens it:

```
PCA_DISPOSABLE_REMOTE_DB_HOST  == the URL's host
PCA_DISPOSABLE_REMOTE_DB_NAME  == the URL's database
PCA_DATABASE_TLS               == REQUIRED
```

Declaring a host therefore does **not** hand over every database on that server.
A remote run announces itself loudly. Local/Compose behaviour is unchanged and
acquires no new required variables, so `npm run db:verify` works exactly as
before. `6/6` tests, each removing one key on its own to prove it is
load-bearing.

## 5. Azure 8.4 — the exact action required

Established read-only via the authenticated Azure CLI. **Nothing was changed.**

```
name      ims-platform          resource group  AppWenPlan
version   8.0.21 (running 8.0.45-azure)
tier      Burstable  Standard_B1ms
location  UAE North             state  Ready
fqdn      ims-platform.mysql.database.azure.com
```

**It does not need to be recreated.** An in-place major-version upgrade is
supported: `az mysql flexible-server upgrade` accepts `--version 8.4`, and
`8.4` is offered in UAE North (the region also offers `9.5`, which PCA does not
support).

```bash
az mysql flexible-server upgrade -g AppWenPlan -n ims-platform -v 8.4
```

**Not run — this is irreversible and causes downtime, and requires explicit
owner authorization.** Take a backup or test on a point-in-time restore copy
first. If the upgrade is declined, the alternative is a new 8.4 flexible server
for the disposable database.
