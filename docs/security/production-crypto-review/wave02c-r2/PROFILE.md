# PCA FamilyEnvelope Crypto Profile V1 — external-review candidate

Status: **qualification candidate only**. This profile is not production-approved, is not wired into the browser runtime, and does not open `CRYPTO_SUITE_APPROVED_FOR_PRODUCTION`. It requires independent review of both `@hpke/core@1.9.0` and this PCA integration.

## 1. Protocol and algorithms

The outer FamilyEnvelope stays protocol major 1, minor 0. The existing canonical envelope serializer and DSK signature contract remain authoritative; this candidate adds a binary encrypted-payload profile and AAD. It does not replace outer serialization or signature verification.

The FDEK key-wrap uses RFC 9180 HPKE Base mode:

| Parameter | Exact value |
|---|---|
| KEM | DHKEM(P-256, HKDF-SHA256), ID `0x0010` |
| KDF | HKDF-SHA256, ID `0x0001` |
| AEAD | AES-128-GCM, ID `0x0001` |
| Mode | Base, mode ID `0x00` |
| Implementation candidate | `@hpke/core@1.9.0`, public `CipherSuite.seal/open` API |
| Provider | WebCrypto P-256 ECDH, HKDF-SHA256 and AES-GCM |

PCA content encryption is a separate FDEK-derived one-use-key profile using WebCrypto HKDF-SHA256 and AES-128-GCM. It is not represented as RFC 9180 HPKE. The external reviewer must explicitly assess this PCA composition, salt/nonce handling, and its relationship to DEC-020. No custom primitive implementation is present.

## 2. Binary payload frame

All integers below are unsigned big-endian. The frame is the decoded outer `payload` bytes; outer JSON uses the existing standard padded Base64 representation. No padding, compression, JSON, or trailing bytes are permitted inside the frame.

Common prefix is 8 bytes: `50 43 41 46 45 32 00 01` (`PCAFE2\0\x01`), followed by one kind byte.

### 2.1 FDEK wrap (kind `0x01`)

The next 6 bytes are suite IDs in order: KEM `00 10`, KDF `00 01`, AEAD `00 01`. Then `enc` is exactly 65 bytes, SEC1 uncompressed P-256 point (`0x04 || x[32] || y[32]`). Then HPKE ciphertext is exactly 48 bytes: 32-byte FDEK followed by the 16-byte AES-GCM tag. Total frame size is exactly 128 bytes. This kind is valid only for `messageType=KEY_ROTATION` and a DEVICE recipient. HPKE's `enc` is fresh for every new seal; identical retries must retransmit the persisted frame rather than reseal.

### 2.2 Content (kind `0x02`)

After kind, a 2-byte content-profile ID is exactly `00 01`, meaning HKDF-SHA256 / AES-128-GCM. Next are salt[32], nonce[12], then ciphertext || tag[16]. Plaintext maximum is 32,768 bytes; ciphertext maximum is 32,784 bytes; frame length is `71 + plaintextLength`, maximum 32,839 bytes. The outer FamilyEnvelope payload limit remains 65,536 bytes. The salt and nonce are freshly generated by WebCrypto for each new envelope and are authenticated in AAD. A content retry must reuse persisted identical ciphertext or create a new messageId; it must never reseal different plaintext under the same message identity.

## 3. FDEK and content key schedule

FDEK is exactly 32 random bytes, scoped to `(familyId, keyEpoch)`. A rotation creates a fresh FDEK. FDEK is wrapped to each current, authorized, non-revoked device; the server receives only opaque envelopes and public metadata.

FDEK-wrap `info` is the exact ASCII byte string `PCA_FDEK_HPKE_INFO_V1` (22 bytes). No terminator. All variable envelope metadata is in AAD.

For each content envelope, derive a 16-byte AES key with WebCrypto HKDF-SHA256:

```text
IKM  = FDEK[32]
salt = frame salt[32]
info = netstrings(
  "PCA_FAMILY_MESSAGE_KEY_INFO_V1",
  "HKDF-SHA256/AES-128-GCM",
  protocolMajor, protocolMinor, messageId, familyId,
  senderDeviceId, recipientKind, recipientIdentifier,
  senderKeyId, messageType, sequenceOrNonce,
  issuedAt, expiresAt, trustSetEpoch, keyEpoch,
  semanticVersion, correlationPresent, correlationValue
)
L    = 16 bytes
```

This is per-envelope derivation; no derived key is reused intentionally. Each AES-GCM key is used for exactly one encryption with one fresh 96-bit nonce. FDEK must not be logged, serialized outside ciphertext, or put in ordinary storage. Browser-side FDEK custody/acquisition is not implemented or approved by this candidate.

## 4. Canonical fields, AAD and byte rules

AAD is a concatenation of strict UTF-8 netstrings, in this exact order:

```text
"PCA_FAMILY_ENVELOPE_AAD_V1",
protocolMajor, protocolMinor, messageId, familyId,
senderDeviceId, recipientKind, recipientIdentifier,
senderKeyId, messageType, sequenceOrNonce,
issuedAt, expiresAt, trustSetEpoch, keyEpoch,
semanticVersion, correlationPresent, correlationValue,
payloadKind, payloadProfile,
[content salt base64url-no-padding, content nonce base64url-no-padding]
```

`payloadKind` is exactly `FDEK_WRAP` or `CONTENT`; profile is exactly `HPKE-0x0010-0x0001-0x0001` or `CONTENT-0x0001`. The final two fields exist only for CONTENT. They encode frame bytes, not caller-provided values.

Each netstring is `ASCII(decimal UTF-8 byte length) || 0x3a || UTF-8 bytes`; decimal has no leading zero except `0`; fields are concatenated with no separator or trailing delimiter. No Unicode normalization occurs. Invalid UTF-16 surrogate sequences are rejected. IDs and metadata follow the existing canonical FamilyEnvelope field order; the existing outer serializer/signature bytes are unchanged. AAD excludes payload and signature to avoid circular input; the existing DSK signature still covers canonical metadata and the complete payload.

Timestamp strings must be valid and exactly `YYYY-MM-DDTHH:mm:ss.sssZ`. Epochs are positive safe integers, encoded as canonical base-10 with no leading zero. `correlationId=null` maps to `0`, empty value; present non-empty value maps to `1`, value. Bounds in UTF-8 bytes: IDs, sender key ID, recipient ID, sequence/nonce, correlation value 128; message type 64; semantic version 32; timestamps 24; epochs 16; version fields 8. Total transcript max 4096 bytes. Only protocol 1.0 is accepted. Envelope lifetime must be positive and at most 24 hours. The receiver rejects malformed, unknown, oversized, expired, or unsupported profile input with one generic PCA crypto failure; it never retries a weaker profile.

## 5. Binding and validation order

The outer DSK signature authenticates the canonical envelope including all routing and meaning-bearing metadata and the complete payload. Before opening ciphertext, callers must strictly parse and canonicalize; verify the sender DSK under the current accepted Trust Set; check family, recipient, Trust Set epoch, key epoch, message type, replay/sequence, expiry and semantic version; then perform AEAD open; then validate the decrypted policy schema. No plaintext may reach the application layer after failed signature, scope, epoch, replay, expiry, or AEAD validation.

AAD repeats the signed metadata bindings for defense in depth: protocol version, messageId, familyId, senderDeviceId, recipient kind and identifier, senderKeyId, messageType, trustSetEpoch, keyEpoch, sequenceOrNonce, issuedAt, expiresAt, semanticVersion, and correlationId presence/value.

## 6. Rotation candidate policy

Every rotation generates a new independent 32-byte FDEK and increments `keyEpoch` by exactly one. New sends use only the current epoch. A normal rotation may retain the immediately previous FDEK for at most 24 hours to open already-issued messages only when their `issuedAt` precedes the rotation effective time and their expiry is no later than effective time + 24 hours. After that boundary the old FDEK is erased/pruned. Emergency revocation rotation erases the previous FDEK immediately and rejects delayed old-epoch envelopes. Rotation never claims retroactive erasure from a device that already learned a prior FDEK. A device revoked before epoch N+1 must not receive or open the N+1 wrap.

## 7. Version and failure behavior

This candidate supports exactly protocol 1.0 and the frame/version bytes above. There is no negotiation. Unknown major/minor, frame kind, profile ID, suite ID, field shape, trailing data, or version downgrade fails closed. There is no plaintext or legacy cryptographic fallback. All cryptographic failures surface as `PCA_ENVELOPE_CRYPTO_FAILED`; error details are not returned and this module emits no logs.

## 8. Scope and limits

The adapter is intentionally not exported through the package entry point and not wired to `cryptoGate.ts` or production composition. It has no browser DEK creation/custody, no FDEK storage, no Parent Web enrollment/recipient-key lifecycle, no inbound production caller, and no iOS/Android executable interoperability in this branch. The `openFdekForDevice` function exists only for candidate vectors/reference checks and does not establish browser production key custody. Browser production E2EE remains closed. Android API 31+ and iOS native key custody are unchanged; no claim is made that this browser candidate makes the complete activation flow production-ready.

The profile is a proposal for independent review, not a frozen production protocol. External review must assess compatibility with existing mobile and backend contracts before any implementation is accepted into authoritative `pca-dev`.
