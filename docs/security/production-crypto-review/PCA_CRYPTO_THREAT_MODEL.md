# PCA Crypto Threat Model

Prepared for the pending human security review of `PRODUCTION_CRYPTO_SUITE = PENDING_HUMAN_SECURITY_REVIEW`. Every entry below states: (a) what the architecture *claims* to defend against (per docs 09/21/22/24 and inline source comments), (b) what is actually *implemented* in source at commit `e9075baa3a6005e1d953024df2b871b4ff38c63b` vs. what is *pending*, and (c) residual risk today.

**Governing fact, stated once here and true for nearly every row below**: because `RejectingDeviceSignatureVerifier` and `RejectingEnvelopeSignatureVerifier` are wired as the production default in `backend/src/main.ts` (and the Android equivalent ships the same default), and because `TrustSetSignatureVerifier`/`RecoveryKdf`/`RecoveryEnvelopeCipher` have **no production wiring of any kind**, essentially every attack whose defense ultimately routes through a signature check or a decrypt operation is **currently moot in production, because the system fails closed before the attacker's specific technique would even matter** — device sessions cannot be issued, envelopes cannot be accepted, FTS epochs cannot be accepted, and recovery cannot complete. This is stated explicitly, per-row, as "residual risk today: moot (fails closed)" rather than repeated as a blanket disclaimer, so the reviewer can see which specific mechanisms *would* matter once a suite is selected, and can evaluate each one on its own logic rather than only on today's blanket rejection.

---

### 1. Malicious client (compromised/hostile family device)

- **Claimed defense**: Per-device DSK signs everything it originates; FTS role authorization (not yet implemented, see `ReceiverPipeline.SenderRoleAuthorizer`) restricts which message types a role may send; a compromised device can be revoked without its cooperation (PCA-SEC-013).
- **Implemented**: Revocation mechanics (FTS entry `status: 'REVOKED'`, `deviceKeysToWrapFdekFor` excludes revoked entries from future FDEK distribution), envelope structural validation, replay/expiry/epoch checks.
- **Pending**: Sender-role authorization (`SenderRoleAuthorizer` is an interface only, no implementation — a malicious device that IS still a trusted signer but sends a message type its role shouldn't be allowed to send would not currently be caught by any implemented check; this is a real, present gap independent of the crypto-suite decision, and should be flagged to the reviewer as a distinct open item, not conflated with the crypto gate). The actual signature check that would catch a device *without* valid key material is `STUB-FAIL-CLOSED`.
- **Residual risk today**: Moot for signature-forgery attempts (fails closed). The sender-role-authorization gap is NOT moot — it is a genuinely unimplemented authorization layer that exists independent of `PRODUCTION_CRYPTO_SUITE`, and should be tracked as its own item.

### 2. Stolen service password (service control-plane account compromise)

- **Claimed defense**: `backend/src/auth/` (`AuthService`, `fastifyAuthPlugin`) issues opaque session tokens; explicitly documented as never conferring family E2EE authority. Single generic 401 for every failure mode (anti-enumeration).
- **Implemented**: Full session issue/validate/revoke lifecycle, TTL policy (`DEFAULT_SESSION_TTL_MS` 12h, `MAX_SESSION_TTL_MS` 30 days), SHA-256 token hashing (raw token never stored), CSPRNG token generation.
- **Pending**: Nothing crypto-suite-dependent — this layer does not depend on `PRODUCTION_CRYPTO_SUITE` at all; it's a distinct, already-implemented control plane.
- **Residual risk today**: A stolen service session grants only "recognized service account" status — `types.ts`'s own comment: "this is not, and must never be treated as, family E2EE authority." A compromised service password does not, by this design, grant access to family plaintext or the ability to forge a valid family envelope/FTS epoch (those require DSK material this layer never touches). Reviewer should independently confirm no HTTP route conflates a valid service session with family-level authority — this review did not exhaustively audit every route handler.

### 3. Stolen browser session (parent-web)

- **Claimed defense**: `parent-web/src/security/secureStorage.ts` documents an intent for non-extractable WebCrypto key storage; not yet implemented.
- **Implemented**: Nothing production-grade. `InMemorySecureStorage` is an explicit dev-only stub, "intentionally NOT persisted across reloads."
- **Pending**: All of it — real browser-side key storage/signing is `NOT_IMPLEMENTED`.
- **Residual risk today**: Moot in the narrow sense that there is no real browser-side signing key to steal yet (the stub never persists real key material). But this is a **forward-looking gap the reviewer must weigh**: whatever real implementation replaces the stub (WebCrypto non-extractable keys, or another mechanism) must itself resist session-token theft leading to unauthorized use of a family DSK from the browser — this is an open design question, not merely a "wait for the crypto suite" item, since it also involves browser storage architecture decisions (IndexedDB, extractable flags, session binding) that a signature-algorithm choice alone won't resolve.

### 4. Server DB breach (backend MySQL compromise)

- **Claimed defense**: PCA-SEC-015 ("PCA support/ops staff MUST NOT be able to recover family plaintext under any workflow"); PCA-SEC-023 ("no Enrollment/Relay schema/table/log/API may hold any readable family content"); PCA-SEC-010 (family content E2E confidential from PCA infra).
- **Implemented**: `backend/test/schema-privacy.test.mjs` exists and is part of the standard test run (passing) — asserts the MySQL baseline migration contains only the approved minimal central-service tables and introduces no prohibited readable/secret fields. `RecoveryRepository`/`MySqlRecoveryRepository` store only the opaque recovery-envelope ciphertext blob; the server never derives or stores a decryption key for it. Relay (`backend/src/relay/`) is documented and (per its own module boundary) implemented as ciphertext-blind store-and-forward.
- **Pending**: The actual guarantee that recovery-envelope ciphertext and family-envelope payload ciphertext are genuinely opaque to the server depends on the pending AEAD/KEM construction being implemented correctly and the server never being handed a decryption key. Today, structurally, the server-side code paths that *would* decrypt do not exist (no `PayloadDecryptor`/`RecoveryEnvelopeCipher` implementation is wired anywhere server-side) — so there is no code path today by which a DB breach could yield plaintext even in principle, because no plaintext-producing code runs server-side.
- **Residual risk today**: Low, but not solely because of the crypto gate — the *architectural* choice to never run decrypt operations server-side is what protects a DB breach today, and that architectural boundary is verified by `schema-privacy.test.mjs` and code-review-level inspection, not by the pending signature/AEAD suite. Reviewer should confirm this architectural boundary (never decrypt server-side) is a load-bearing invariant that also survives whatever concrete crypto suite is eventually chosen — i.e., the suite decision must not introduce a server-side decrypt capability as an implementation convenience.

### 5. Relay ciphertext theft (attacker intercepts/exfiltrates queued envelopes)

- **Claimed defense**: PCA-SEC-010 (E2E confidentiality); envelope `payload` is opaque ciphertext at every layer it passes through (backend relay, runtime-sync wire codec, Android runtime) — verified by direct source reading: `envelopeWireCodec.ts`/`.kt` both explicitly never inspect/transform `payload`.
- **Implemented**: The ciphertext-blind transport chain itself (relay storage, wire codec, HTTP surface) is fully implemented and tested. Structural confidentiality (nothing server-side ever branches on payload contents) is real today.
- **Pending**: The actual AEAD construction that makes `payload` cryptographically opaque (vs. merely "nothing currently parses it") is not yet selected/implemented. Today `payload` is genuinely just an opaque `Buffer` produced by whatever the device-side sender puts there — there is no confirmed AEAD guarantee behind it in this backend tree, because no encryption implementation exists to inspect.
- **Residual risk today**: Cannot be assessed as "protected by encryption" today in the cryptographic sense — the transport-level opacity (nothing server-side reads it) is real, but the confidentiality-under-compromise guarantee (an attacker with ciphertext cannot recover plaintext) depends entirely on a suite that does not yet exist. Reviewer should treat `payload`'s actual content today as whatever the device-side test/dev harness puts there, not as production-strength ciphertext.

### 6. Device theft (physical device compromise)

- **Claimed defense**: Android Keystore-backed local-at-rest encryption for the local Room database (`AndroidKeystoreLocalRecordCipher`); device revocation removes a stolen device's ability to receive future FDEK material; DSK/DEK are meant to be non-exportable, Keystore/Secure-Enclave-backed (doc 09 Section 3.1, `VERIFIED_WITH_LIMITATION` per doc 09/04's platform table — hardware backing varies by device tier).
- **Implemented**: `AndroidKeystoreLocalRecordCipher` is real, production AES-256-GCM with a non-exportable Keystore-generated key — this genuinely protects the local Room DB file against extraction today, independent of the family-E2EE crypto gate (its own doc comment explicitly disclaims any relation to `PRODUCTION_CRYPTO_SUITE`). Revocation-then-rotation state machine is fully implemented in `familytrustset`.
- **Pending**: Whether the DSK/DEK key pairs themselves will actually be generated/held inside Android Keystore (hardware-backed, non-exportable) vs. some other storage is not yet decided/implemented — no DSK/DEK generation code was found anywhere in the Android `runtime/sync/envelope/` package; only the local-record-cipher key (a *different* key, for a *different* purpose) uses Keystore today.
- **Residual risk today**: A stolen device today has no functioning family-envelope signature capability to physically extract, because no DSK signing implementation exists yet on Android to steal from. Once implemented, the reviewer must confirm DSK/DEK material is genuinely non-exportable from the platform keystore (not just "keystore-adjacent" like the local-record-cipher key, which is a distinct, lower-stakes key by the module's own admission).

### 7. Replay attacker (captured envelope/challenge resubmitted)

- **Claimed defense**: PCA-SEC-021 ("receiving device MUST reject any already-processed sequence/nonce per sender key"); PCA-SEC-022 (every acceptance check independent).
- **Implemented**: `ReplayLedger`/`InMemoryReplayLedger` (bounded 4096 entries/sender, oldest-eviction) — fully implemented and tested. Device-auth challenge replay is closed atomically at the repository layer (`consumeAtomically`, verified concurrency-safe by test "verifyChallenge REPLAY-PROOF under genuine concurrency: N simultaneous verifications of the identical valid signature -- exactly one succeeds"). Recovery-transaction replay is closed by `RecoveryTransactionLedger.claimTransaction`'s single-atomic-operation contract (also red-team tested, scenario 1: "recovery replay").
- **Pending**: None of the replay-ledger mechanics themselves depend on the pending crypto suite — this is genuinely production-ready bookkeeping today.
- **Residual risk today**: Low for the ledger mechanics themselves (real, tested, not gated). The overall attack is still moot end-to-end in production because a captured/replayed item still needs to pass the currently-fail-closed signature check to matter in the first place — but the replay-ledger logic itself would hold up correctly the moment a real verifier is wired in, which is a meaningfully stronger position than "nothing is implemented yet."

### 8. Rollback attacker (attacker resubmits a stale but validly-signed lower-version envelope/epoch, or manipulates device clock)

- **Claimed defense**: Anti-downgrade floors on `trustSetEpoch`/`keyEpoch` (both `FamilyEnvelopeVerifier` and `FamilyTrustSetEngine`); strict version-increase for `POLICY_UPDATE`; `SIGNED_ROLLBACK` as an explicit, distinct message type rather than a relaxed monotonicity check (doc 22 Section 6); `TrustedTimeHighWaterMark` for clock-rollback detection (doc 21 Section 3, doc 11 Section 5.1).
- **Implemented**: All floor checks are implemented and tested (`verifier.test.mjs`, `engine.test.mjs`). `TrustedTimeHighWaterMark.evaluateDeviceClock`/`advanceHighWaterMark` is fully implemented, monotonic by construction, and — per its own doc comment — is a genuinely new mechanism not previously present anywhere in the codebase. Recovery red-team scenario 11 ("clock manipulation") explicitly confirms `acceptRecoveryEpoch` never reads `issuedAt` against wall-clock time — only epoch numbers gate acceptance, so an absurd future `issuedAt` neither helps nor hinders acceptance; this is a deliberate design choice, verified by test, not an oversight.
- **Pending**: The signature check that would ultimately validate whether a rollback attempt's claimed signer is genuine is `STUB-FAIL-CLOSED`/`NOT_IMPLEMENTED` depending on which path (envelope vs. FTS).
- **Residual risk today**: The floor/monotonicity logic itself is real and tested — a rollback attempt against a *lower version with a validly-forged-looking signature* would be caught by version/epoch floor checks today even before signature verification is reached (cheap checks run first), so this defense-in-depth layering is genuinely exercised. Full end-to-end protection against a rollback with a *genuinely valid* signature (the actual threat once a suite exists) is not yet testable, since no real signature can currently be produced.

### 9. Cross-family attacker (attacker with legitimate access to Family A attempts to act against Family B)

- **Claimed defense**: Family-scoped device lookups throughout (`DeviceRepository.findDeviceForFamily`, never `findDeviceUnscoped` from an authenticated-caller path); `FAMILY_MISMATCH` rejection in both `FamilyTrustSetEngine.acceptEpoch` (defense-in-depth, "should never legitimately fire" per its own comment) and `FamilyTrustSetRecoveryEngine.acceptRecoveryEpoch`; cross-family IDOR closure in `OutboundRelayService` (`recipientDeviceId` must resolve to a real device in the same family as the verified sender session).
- **Implemented**: All of the above, fully tested. Recovery red-team scenario 9 ("cross-family recovery") explicitly confirms a validly-opened envelope for Family A cannot authorize a recovery epoch claiming to be Family B. IDOR-style tests exist across `authz`, `childprofiles`, `familyrbac` test suites (e.g. "IDOR: a scope granted for family A cannot be used to authorize an operation on family B, even for the same account" — `authz/service.test.mjs`, part of the full passing suite).
- **Pending**: Nothing specific to the crypto suite for this category — cross-family isolation is enforced by ID-scoping logic, not by the pending signature algorithm.
- **Residual risk today**: Low. This is one of the more mature, already-defended categories in the reviewed tree, independent of the crypto gate. One documented, NOT-crypto-gated open item: `DeviceRepository.findDeviceUnscoped`'s own doc comment flags that `DeviceAuthService.issueChallenge`'s use of it is not yet safely bindable if directly exposed over HTTP to an arbitrary caller (a potential cross-family device-existence/revocation-status enumeration oracle) — `DeviceSessionService.issueChallengeSafely` appears to begin closing this, but the underlying repository-layer comment still calls it unresolved. Reviewer should independently confirm this is fully closed before any HTTP route exposes raw challenge issuance.

### 10. Malicious/stale parent endpoint (a parent-side session/device that is compromised, or that is running stale/superseded trust-set state)

- **Claimed defense**: `EPOCH_STALE`/`DEVICE_OFFLINE` tamper states (doc 21 Section 2); `TamperStateEngine.computeConvergenceState`/`computeOverallState`; revocation propagation via FDEK rotation (PCA-SEC-019).
- **Implemented**: `TamperStateEngine` is fully implemented and tested (23 tests), with an exhaustive `CONDITION_POLICY` map and precedence ordering (`REVOKED` outranks everything). Composes with, rather than duplicates, `familysync/connectionState.ts`.
- **Pending**: The actual cryptographic proof that a given endpoint is who it claims (signature verification) is stub-fail-closed.
- **Residual risk today**: The state-machine logic that would *react* to a stale/malicious endpoint (marking it `EPOCH_STALE`, excluding it from FDEK rotation targets, etc.) is real and tested. Detection of genuine malice (vs. honest staleness) still depends on the pending signature suite for anything requiring cryptographic proof of identity.

### 11. Lost Recovery Secret (RS)

- **Claimed defense**: PCA-SEC-018 — explicit, mandatory, offline acknowledgement at family creation that losing both the RS and all active parent devices makes recovery permanently impossible; doc 08 PCA-FR-144 — no support-agent bypass exists.
- **Implemented**: The *architectural* stance (no bypass exists anywhere in source — confirmed by the absence of any "admin override" parameter in `acceptRecoveryEpoch`'s signature, explicitly tested in red-team scenario 8: "the function's signature has exactly 5 parameters, pinning the API shape so a future 'adminOverride' addition would be caught in review"). This is a genuinely strong, tested guarantee against a *future* accidental or malicious bypass being added.
- **Pending**: The RS itself (its generation, presentation-at-creation flow, and the KDF that derives the RWK from it) has no implementation yet — `RecoveryKdf.ts` is interface-only.
- **Residual risk today**: The "no bypass" guarantee is real and tested today, which is a meaningful, independently valuable property regardless of the crypto suite status. The RS/RWK mechanics themselves are entirely unbuilt, so there is no working recovery flow to lose access to yet, in either direction.

### 12. Backend restart / durability (in-memory ledgers losing state on restart)

- **Claimed defense**: Not explicitly claimed as solved by this lane; doc references Agent 20's separate durability work conceptually (not independently verified in this pass, per task scope — that work may exist on a different branch not present in this worktree).
- **Implemented**: `InMemoryReplayLedger`, `InMemoryDataVersionLedger`, `InMemoryMessageIdempotencyLedger`, `InMemoryFamilyTrustSetStore`, `InMemoryRecoveryTransactionLedger`, `InMemoryDeviceSessionRepository`, `InMemoryTamperEventLedger`, `InMemoryRecoveryTransactionStore` are ALL explicitly documented as "real, usable defaults, not test-only stand-ins" for ordinary (non-crypto-sensitive) bookkeeping — but every one of them is in-memory and would lose all state on a backend process restart. `DeviceChallengeRepository`, `AuthRepository`, `DeviceRepository`, `EnrollmentRepository`, and `RecoveryRepository` all have MySQL-backed production implementations; `DeviceSessionRepository` and `RecoveryTransactionLedger`/`RecoveryTransactionStore` do **not** — this is a specific, named gap (Section 15/12 of the source map).
- **Pending**: A durable implementation of the replay ledger, version ledger, message-idempotency ledger, FTS store, and recovery-transaction ledger for a real production device/family (each interface is designed to be swapped for a durable implementation without changing calling code, per multiple doc comments — but no such durable implementation exists in this reviewed tree for the family-security-critical ledgers).
- **Residual risk today**: On the backend side specifically, a restart of the process holding `InMemoryDeviceSessionRepository` invalidates all live device sessions (forcing re-authentication, which is a safe failure mode, not a security hole) and a restart holding `InMemoryRecoveryTransactionLedger`/`Store` would lose in-flight recovery-transaction dedupe state — the code comments flag this as an explicit scope limitation, and a durable implementation preserving the same atomicity contracts (e.g. `INSERT ... ON CONFLICT DO NOTHING` for the recovery-transaction ledger) is called out as required before production use. This is a genuine, named gap independent of the crypto-suite decision. If Agent 20's durability work has addressed this on another branch, it was not visible in this worktree and this package cannot verify its content.

### 13. Clock manipulation

- **Claimed defense**: doc 21 Section 3 (clock-rollback response), doc 11 Section 5.1; `TrustedTimeHighWaterMark`.
- **Implemented**: `evaluateDeviceClock`/`advanceHighWaterMark` fully implemented and tested (7 tests): rollback detection, monotonic pinning at the high-water mark rather than the rolled-back reading, and — critically — `advanceHighWaterMark` never regresses the persisted mark even during an active rollback. Recovery-path clock independence separately confirmed (red-team scenario 11, see item 8 above).
- **Pending**: Nothing specific to the crypto suite.
- **Residual risk today**: Low for the mechanism itself — this is a genuinely new, tested, monotonic-by-construction defense. Reviewer should confirm the high-water mark's own persistence layer (wherever it is actually stored on-device) is itself tamper-resistant, since this module only defines the pure evaluation logic, not its storage.

### 14. Nonce misuse (reuse, predictability, insufficient entropy)

- **Claimed defense**: `generateChallengeNonce` uses `node:crypto.randomBytes(32)` (CSPRNG); envelope `sequenceOrNonce` is caller-supplied (either a numeric sequence or an opaque nonce, per doc 22 Section 3) and checked only for replay (uniqueness), not generated by this backend tree.
- **Implemented**: The device-auth challenge nonce generation is real, CSPRNG-backed, and tested (`nonce.test.mjs`: "generateChallengeNonce produces a plausible, unique nonce each call"). The envelope `sequenceOrNonce` field's *generation* is entirely a device-side (sender's) responsibility not modeled in this backend tree — the backend only ever validates shape and replay-uniqueness of whatever value it's given.
- **Pending**: Whatever AEAD construction is eventually chosen will introduce its own nonce (IV) requirements distinct from `sequenceOrNonce` (which is an application-level replay-protection value, not necessarily the same as an AEAD nonce) — this mapping has not been designed yet, since no AEAD implementation exists.
- **Residual risk today**: Low for the one nonce genuinely generated by this backend (device-auth challenge). The eventual AEAD nonce-uniqueness-under-concurrent-use property (a classic AEAD pitfall — nonce reuse catastrophically breaks confidentiality/integrity for most AEAD constructions) is squarely a reviewer decision point once a suite is chosen, and should be an explicit checklist item (see `PCA_CRYPTO_REVIEWER_CHECKLIST.md`).

### 15. Concurrent message races

- **Claimed defense**: PCA-SEC-022 (independent checks); atomic claim-before-mutate patterns throughout (`DeviceChallengeRepository.consumeAtomically`, `RecoveryTransactionLedger.claimTransaction`, `EnrollmentRepository`'s single-transaction invitation-redemption-plus-device-creation).
- **Implemented**: Extensively tested for the specific races that exist in implemented code: device-challenge concurrent-replay (test explicitly verifies "N simultaneous verifications of the identical valid signature -- exactly one succeeds"), recovery-transaction double-claim (`RecoveryTransactionLedger`'s single-atomic-operation contract, explicitly not a check-then-write pair, with an explicit comparison in its own comment to "the PCA-3 lane's NF-002 fix for the identical defect in a different domain"), and `acceptRecoveryEpoch`'s own optimistic-concurrency re-check (`CONCURRENT_EPOCH_CHANGED`) against two racing recovery attempts both passing validation against the same stale snapshot before either writes.
- **Pending**: Nothing specific to the crypto suite for the race-safety mechanics themselves.
- **Residual risk today**: Low for the specific races that are implemented and tested. Reviewer should independently confirm, once a real encryption implementation exists, that no new race is introduced by whatever key-caching/session-key-derivation approach is chosen (e.g. two concurrent envelope-encrypt operations under the same FDEK+nonce-derivation scheme must never be able to produce nonce collisions) — this is exactly PCA-DEC-020's open forward-secrecy/session-key-derivation decision, not yet resolved.

## Summary for the reviewer

The pattern across nearly all 15 rows is consistent: **the protocol logic, state machines, ledgers, and race-safety mechanics are substantially implemented and tested** (928/928 tests passing across the full backend suite; 243/243 in the crypto-adjacent subset — see `PCA_CRYPTO_TEST_EVIDENCE.md`), while **every seam requiring an actual cryptographic algorithm decision (signature scheme, AEAD, KDF/KEM) is deliberately unimplemented**, either as a fail-closed stub wired into production (device-auth, family-envelope) or as a completely unwired interface (FTS trust-set signatures, recovery KDF, recovery envelope cipher). Two gaps exist that are **independent of the crypto-suite decision** and should be tracked separately by the reviewer: (1) sender-role authorization (`SenderRoleAuthorizer`) has no implementation at all, and (2) `DeviceRepository.findDeviceUnscoped`'s cross-family enumeration-oracle risk is flagged as not fully closed if challenge issuance is ever exposed directly over HTTP without additional binding.
