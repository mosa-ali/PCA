# PCA Crypto Reviewer Checklist

A concrete, source-grounded checklist for the human security reviewer deciding whether/how to resolve `PRODUCTION_CRYPTO_SUITE = PENDING_HUMAN_SECURITY_REVIEW`. Each item is tailored to something specific found in source during this review, not generic boilerplate — the source citation is given so the reviewer can verify the premise independently. Use `PCA_CRYPTO_REVIEW_FINDINGS_TEMPLATE.md` to record findings against these items.

## A. Algorithm/suite selection decisions (PCA-DEC-020, PCA-DEC-021)

- [ ] **A1.** Select a concrete signature algorithm for DSK operations (candidates named in doc 09: Ed25519 vs. ECDSA-P256; encoding; domain-separation prefix) and confirm it will be implemented identically behind `DeviceSignatureVerifier`, `EnvelopeSignatureVerifier`, and `TrustSetSignatureVerifier` — all three interfaces are currently separate, unimplemented seams (`backend/src/deviceauth/DeviceSignatureVerifier.ts`, `backend/src/familyenvelope/EnvelopeSignatureVerifier.ts`, `backend/src/familytrustset/TrustSetSignatureVerifier.ts`) with textually near-identical doc comments citing the same pending decision — confirm the reviewer intends one algorithm for all three, not divergent choices.
- [ ] **A2.** Select the AEAD/KEM construction for `RecoveryEnvelopeCipher.open()` (`backend/src/recovery/RecoveryEnvelopeCipher.ts`). Doc 09 Section 3.4 names RFC 9180 HPKE as a *candidate*, not a decision — confirm or reject this candidate explicitly.
- [ ] **A3.** Select the KDF for `RecoveryKdf.derive()` (`backend/src/recovery/RecoveryKdf.ts`) that turns the offline Recovery Secret into the ephemeral RWK — candidates cited only generically (Argon2id, scrypt, PBKDF2, HKDF) with no recommendation in source. Given the RS is meant to be high-entropy (not a low-entropy human password per PCA-SEC-018's framing), confirm whether a memory-hard KDF (Argon2id/scrypt) is actually necessary here vs. a simpler HKDF being sufficient — this changes implementation complexity meaningfully and should be a deliberate choice, not a default.
- [ ] **A4.** Resolve PCA-DEC-020's forward-secrecy question explicitly: full ratchet-style construction vs. simpler per-envelope AEAD keyed from the current FDEK with rotation-on-revocation. The doc's own recommendation is the simpler option for initial launch — confirm the reviewer agrees, since this materially affects what "Message/session keys" (Section 3 of the review package) end up being in source, and no such type exists in the codebase yet either way.
- [ ] **A5.** Decide whether `RecoveryEnvelopeCipher.open()`'s AEAD payload will also cover the FDEK(s) it wraps with authenticated associated data binding `familyId`, envelope ID, epochs, and suite IDs exactly as doc 09 Section 3.4 specifies — verify the eventual concrete implementation's associated-data construction against that exact field list, not an approximation of it.

## B. Nonce/IV discipline

- [ ] **B1.** Confirm nonce/IV uniqueness is structurally guaranteed (not merely "unlikely to collide") for concurrent envelope encryption under the same FDEK — envelope `sequenceOrNonce` (`familyenvelope/types.ts`) is an *application-level replay-protection* value, distinct from whatever AEAD nonce the eventual cipher construction uses; confirm these are not conflated in the concrete implementation, and that the AEAD nonce specifically cannot repeat under concurrent same-key encryption (e.g. via counter-based construction with a hard uniqueness invariant, not caller-supplied randomness alone).
- [ ] **B2.** Confirm the device-auth challenge nonce (`deviceauth/nonce.ts`'s `generateChallengeNonce`, currently `node:crypto.randomBytes(32)`) is not repurposed as, or conflated with, any AEAD nonce in the eventual implementation — it is currently scoped only to challenge/response replay protection.
- [ ] **B3.** Confirm nonce reuse is impossible under concurrent envelope creation from the same device — i.e., if two envelopes are constructed concurrently on the same device under the same `keyEpoch`, verify the concrete implementation cannot produce two envelopes with the same AEAD nonce even under a process crash/restart between them (a counter-based nonce whose counter is not durably persisted before use would violate this).

## C. Signature verification implementation correctness

- [ ] **C1.** Confirm the concrete signature verification implementation uses constant-time comparison for the signature-check itself (not e.g. a byte-by-byte `===`/`memcmp`-equivalent that could leak timing information about how many leading bytes matched) — none of the three verifier interfaces currently have any implementation to check, so this must be explicitly required of whatever is submitted to replace `RejectingDeviceSignatureVerifier`/`RejectingEnvelopeSignatureVerifier`/(the currently-unwired) `TrustSetSignatureVerifier`.
- [ ] **C2.** Confirm the eventual concrete `EnvelopeSignatureVerifier`/`TrustSetSignatureVerifier`/`DeviceSignatureVerifier` implementations, once written, are covered by tests that supply a **deliberately invalid** signature of the *correct length/format* (not just a malformed/wrong-length one) — the current test suites all use test-only doubles for "valid" signature simulation and structural-validity checks (`policy.ts`'s `isPlausibleSignature`, a length-only bound: 1–512 bytes) for malformed input; no test today exercises a well-formed-but-cryptographically-wrong signature against a real algorithm, because none exists yet.
- [ ] **C3.** Confirm `publicKey` role separation is enforced not just by convention/comment but is impossible to violate at the type or runtime level in the concrete implementation: every verifier interface's doc comment states "a DEK must never be accepted here" for signature checks, and `familytrustset/policy.ts`'s `isDistinctKeyPair` / `FamilyTrustSetEngine.findDuplicateIdentity` structurally prevent a DSK and DEK from being the same key material or cross-assigned between entries — confirm the concrete signing implementation cannot be handed a DEK and produce a syntactically valid "signature" that would pass `isPlausibleSignature`'s shape check.
- [ ] **C4.** Confirm `MAX_SIGNATURE_LENGTH = 512` bytes (`familyenvelope/policy.ts`, `familytrustset/policy.ts`) is sufficient for the chosen algorithm's actual signature size (e.g. Ed25519 signatures are 64 bytes — comfortably under; some ECDSA encodings with certain curve/format choices could vary) — verify this constant does not need updating for the chosen suite, and if it does, update it deliberately rather than let a working signature silently exceed the parser's bound and be rejected as `INVALID_SIGNATURE`-shaped-as-parse-failure.

## D. Recovery-secret and recovery-envelope correctness

- [ ] **D1.** Confirm the Recovery Secret cannot be derived, reconstructed, or brute-forced from any single compromised party's data — specifically: the server's stored opaque recovery-envelope ciphertext (`RecoveryRepository`/`MySqlRecoveryRepository`, which the server can read directly from its own DB) must not, combined with any other server-known value, be sufficient to derive or brute-force the RS or RWK. Verify this holds for whatever concrete KDF/AEAD is chosen — e.g. if the KDF salt is server-stored alongside the ciphertext (as doc 09 Section 3.4 says it may be, since salt is listed as part of the envelope's own recorded fields), confirm salt alone does not meaningfully reduce RS search space.
- [ ] **D2.** Confirm `acceptRecoveryEpoch`'s existing structural guarantees remain true once real crypto is wired in — re-run the 11 red-team scenarios in `backend/test/familytrustset/recoveryRedTeam.test.mjs` against the real `TrustSetSignatureVerifier`/`RecoveryEnvelopeCipher` implementations once they exist (today they run only against test-only doubles) and confirm all 11 still reject as designed.
- [ ] **D3.** Confirm the recovery flow's one-time `recoveryTransactionId` claim (`RecoveryTransactionLedger.claimTransaction`) will be backed by a genuinely durable, atomic store in production — the only implementation today is `InMemoryRecoveryTransactionLedger`, explicitly documented as needing a durable equivalent (e.g. `INSERT ... ON CONFLICT DO NOTHING`) preserving the exact same atomicity contract before production use; confirm this durable implementation exists and has its own concurrency test before recovery is enabled for real families.
- [ ] **D4.** Confirm `OpenedRecoveryEnvelope`'s epoch-binding checks (`opened.boundTrustSetEpoch > currentEpoch.trustSetEpoch` / `opened.boundKeyEpoch > currentEpoch.keyEpoch` rejected as `ENVELOPE_EPOCH_MISMATCH`, in `FamilyTrustSetRecoveryEngine.ts`) correctly reflect whatever epoch-binding fields the real `RecoveryEnvelopeCipher.open()` actually authenticates as associated data — this check currently trusts whatever `OpenedRecoveryEnvelope` claims once cipher-opened successfully; confirm the real cipher implementation cannot be tricked into "opening successfully" with attacker-influenced epoch-binding fields that were not actually part of the authenticated associated data.

## E. Sender-role authorization (independent of crypto suite, but must not be forgotten)

- [ ] **E1.** Implement `SenderRoleAuthorizer` (`familyenvelope/ReceiverPipeline.ts`) before enabling real signature verification — a validly-signed message from a role not authorized to send that `messageType` is currently **not rejected by any implemented check** (only by the not-yet-implemented interface). This is not blocked on crypto suite selection and should not be silently deferred behind it.
- [ ] **E2.** Confirm the eventual `SenderKeyResolver` implementation (also `ReceiverPipeline.ts`, unimplemented) resolves `senderKeyId` to a currently-*trusted* key strictly from the locally-verified FTS (never from a server-asserted value) — per PCA-SEC-017's "every device MUST independently verify... against its own locally-held copy," confirm no implementation path lets a server response substitute for local FTS state here.

## F. Payload decryption/authorization

- [ ] **F1.** Confirm `PayloadDecryptor.decrypt()` (unimplemented interface, `ReceiverPipeline.ts`) returns `null` on **any** authentication failure — never partial or best-effort plaintext — matching its own doc comment's requirement, once implemented.
- [ ] **F2.** Confirm `PayloadSchemaAuthorizer` (also unimplemented) is wired in before any decrypted payload is acted upon, so a validly-decrypted-but-role-inappropriate payload (e.g. a `POLICY_UPDATE` touching a setting the sending role isn't allowed to set) is still rejected post-decrypt.

## G. Cross-platform consistency

- [ ] **G1.** Confirm the Android `EnvelopeSignatureVerifier.kt` and backend `EnvelopeSignatureVerifier.ts` implementations, once both exist, verify signatures identically given the same `canonicalBytes` — the canonicalization schemes (`familyenvelope/canonicalize.ts` vs. whatever Android-side canonicalizer exists) must produce byte-identical output for the same logical envelope, or cross-platform signature verification will silently and permanently fail. This review did not find a canonicalizer implementation on the Android side (only the wire codec, `EnvelopeWireCodec.kt`) — confirm where/how Android performs canonicalization before signing or verifying, since it was not located during this review.
- [ ] **G2.** Confirm the browser/parent-web side (currently `parent-web/src/security/secureStorage.ts`, an explicit dev stub) will use the same canonicalization and signature scheme as backend/Android — no browser-side envelope construction/verification code exists yet to check.
- [ ] **G3.** Confirm iOS is explicitly scheduled as future work, not silently assumed "the same as Android" — no iOS Keychain/CryptoKit code exists anywhere in source at the reviewed commit, and no iOS-specific crypto design commitment exists in the architecture docs beyond generic cross-platform language.

## H. Operational/production-readiness gaps adjacent to (but not identical to) crypto suite selection

- [ ] **H1.** `DeviceSessionRepository` is in-memory-only (`runtime-sync/DeviceSessionRepository.ts`, `InMemoryDeviceSessionRepository`) with no MySQL-backed implementation — confirm this is acceptable for launch (sessions lost on restart force re-auth, a safe failure mode) or require a durable implementation before enabling real device sessions at scale.
- [ ] **H2.** `DeviceRepository.findDeviceUnscoped`'s doc comment flags an unresolved cross-family device-existence/revocation-status enumeration-oracle risk if challenge issuance is ever exposed directly over HTTP without additional binding — confirm this is closed (verify `DeviceSessionService.issueChallengeSafely`'s fake-challenge synthesis fully addresses it) before any HTTP route reaches `issueChallenge` with a caller-supplied `deviceId`.
- [ ] **H3.** Confirm `MAX_PAYLOAD_BYTES = 64 * 1024` (`familyenvelope/policy.ts`) is sufficient headroom for the chosen AEAD construction's ciphertext expansion (tag size, any KEM-wrapped key material embedded per-message) relative to the largest legitimate plaintext payload this system needs to carry.
- [ ] **H4.** Confirm the one high-severity `npm audit` advisory surfaced during `npm install` in `backend/` (observed during this review's test run, not otherwise investigated) is triaged before this suite decision is finalized, in case it affects any dependency the chosen crypto suite would rely on.

## I. General review discipline

- [ ] **I1.** Confirm no implementation submitted to replace any `Rejecting*Verifier` ever returns `true` unconditionally, performs a format-only check without real cryptography, or otherwise takes a shortcut — this is explicitly warned against in the existing stub's own doc comment (`RejectingCryptoVerifiers.ts`: "DO NOT replace these with a verifier that returns true, a signature-format check without real cryptography, or any other shortcut").
- [ ] **I2.** Confirm PCA-SEC-016 ("no custom/home-grown cryptographic primitives") is honored by whatever concrete implementation is submitted — use well-reviewed libraries/constructions, not a bespoke implementation of any primitive.
- [ ] **I3.** Re-run the full backend test suite (`cd backend && npm test`, currently 928/928 passing) and the Android test suite after wiring in real implementations, and confirm the pass count does not regress and that no test was silently weakened (e.g. a signature-verification test that used to assert `INVALID_SIGNATURE` for a tampered field now needs to assert it against a *real* forged signature, not just a test double).

## J. New crypto-adjacent surface added after this package's reviewed commit (`e9075baa`) — re-audited at commit `332af53d`, 2026-08-23

Feature work landed after the original review pack (PCA-FR-130 bonus-time requests/direct grants, PCA-FR-131 install approval, the family-RBAC removal/disable consolidation, browser trusted-endpoint pairing, self-service parent registration genesis, protection alerting) added the crypto-adjacent seams below. None of them replace, weaken, or bypass `RejectingCryptoVerifiers.ts` or any other existing fail-closed default — re-verified directly against source, not inferred from commit messages — but the original checklist predates all of them, so this section gives the reviewer the same source-grounded treatment for each. Full detail and file:line citations are in `PCA_CRYPTO_SOURCE_MAP.md`'s ADDENDUM (Sections 23–30).

- [ ] **J1.** `backend/src/parentaccount/genesisDeviceSigner.ts` implements real Ed25519 sign/verify (`node:crypto`) for the self-registration genesis-attestation bootstrap — the one place in `backend/src` where a concrete signature algorithm is actually implemented today (not merely test tooling). It is structurally inert in production (`main.ts:303-308` wires the genesis chain engine with `RejectingDeviceSignatureVerifier`, so this real signature is rejected exactly like a forged one), but if/when a `DeviceSignatureVerifier` implementation is approved under A1, confirm explicitly whether this genesis path should keep using Ed25519 or be re-pointed at whatever suite is chosen — do not let this pre-existing candidate silently become the de facto answer to A1 by inertia.
- [ ] **J2.** `parent-web/src/security/trustedEndpointKeyStore.ts` implements real, non-extractable ECDSA P-256 WebCrypto key generation/signing for browser trusted-endpoint pairing (distinct from, and more advanced than, `secureStorage.ts`'s dev-only stub this checklist's G2 item and the source map's Section 8/13 originally described). Before granting browsers "trusted" status in production, confirm: (a) this matches whatever curve/algorithm A1 ultimately selects for device DSKs generally (a browser endpoint is a family device like any other per doc 09 Section 3.1); (b) the three still-missing steps documented in `realTrustedBrowserProvider.ts`'s own header (browser-endpoint device enrollment, challenge-response session issuance, and a real parent-approval-to-TRUSTED ceremony backed by a signed FTS) are implemented together, not partially, since a partial implementation could let a browser reach a session token without ever having a family role/entry the receiving side can trust.
- [ ] **J3.** Confirm the family-action role-resolution seam (`backend/src/familyrbac/TrustSetRoleResolver.ts`) — now the shared authorization gate behind PCA-FR-130 (`ChildRequestService.decide`/`.grantDirectly`), PCA-FR-131's parent-decision half, Safe Zone policy changes, and all three `RemovalDecisionAuthority` decision modes — is wired to the SAME reviewed, signature-verified `FamilyTrustSetStore` this checklist's A/C items already govern, not a second, independently-decided trust source. `FamilyTrustSetRoleResolver` (the real implementation, currently unused in production) already reads that store; there is no separate algorithm decision to make here, but confirm no future change gives this resolver a different, unreviewed data source (e.g. a cached role claim from a service-session token) as a shortcut once product pressure to "just make PCA-FR-130 work" appears.
- [ ] **J4.** `RemovalDecisionAuthority.decideWithLocalPin` (`backend/src/familyrbac/RemovalDecisionAuthority.ts`) is a REAL, PRODUCTION-REACHABLE decision path TODAY, independent of `PRODUCTION_CRYPTO_SUITE` — it is not blocked on this review at all, unlike its two signed/recovery-authorized siblings. If this checklist's reviewer's mandate is limited to `PRODUCTION_CRYPTO_SUITE`, explicitly note that the Administration PIN mechanism (`AdministrationPinService`) granting real removal/disable authority today has its own, separate review need that this document does not cover — do not let silence here be read as "already reviewed."
- [ ] **J5.** No HTTP-level "production wiring is airtight" test exists yet for the PCA-FR-130/PCA-FR-131 routes or the `RemovalDecisionAuthority.decideWithSignedRemoteParent` route, analogous to `backend/test/runtime-sync/http/productionCryptoGateFailClosed.test.mjs`'s coverage of the device-auth/envelope surface (which proves, over real HTTP request/response cycles, that no attacker strategy — including a signature a test-only verifier would accept — can succeed). Unit-level tests for these newer paths use injected test doubles for `TrustSetRoleResolver`/`DeviceSignatureVerifier`, which correctly proves the business logic but does not independently re-prove that `main.ts`'s actual wiring is what ships. Recommend an equivalent HTTP-level regression test for these routes before or alongside the crypto suite activation, so the same "even a signature a test-only verifier would accept still gets 401/403 against the real wiring" guarantee exists for every decision surface, not only the original two.
