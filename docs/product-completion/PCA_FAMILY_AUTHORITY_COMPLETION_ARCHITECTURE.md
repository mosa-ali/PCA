# Family Authority Completion Architecture

Read-only investigation, 2026-08-27, session fork of the PCA product-completion programme. Scope: define the minimum repository architecture required to close the four remaining actionable P0s (`/children/:childId/screen-time`, `/children/:childId/apps`, `/family/members`, `/security/audit`) as ONE coordinated package, not four independently-invented backend authority models.

## Executive finding

The Stage-0 audit's framing of these four routes as "no family-authority backend exists" is only half true. **The authorization decision engine already exists, is real, is tested, and is already wired into two production routes** (`RemovalDecisionAuthority` for device removal/disable, and `childRequestRoutes.ts`'s bonus-time/request decisions). What is actually missing is:

1. One data source: a real, server-reachable `TrustSetRoleResolver` (currently `UnavailableTrustSetRoleResolver`, hardcoded to `NO_TRUST_SET`) — the exact same crypto/trust-distribution gate that already blocks Dashboard, Requests, Safe Zone, Retention, and every other "real but externally gated" P0/P1 finding this session has already catalogued.
2. A handful of new, narrow HTTP routes that call the existing `ParentActionAuthorizationService` with operations that **already exist** in `ParentOperation` (`EDIT_CHILD_POLICY`, `ADD_VIEWER`, `REMOVE_NON_OWNER_PARENT`, `ADD_ADMINISTRATOR`, `CHANGE_ROLE`), following the exact route-registration convention already used by `childRequestRoutes.ts` and the removal-decision routes.
3. Two small, mechanical schema/persistence additions (a membership/invitation table shaped like the existing `enrollment_invitations` table; nothing for screen-time/apps, which needs no new table at all — see POLICY_WRITE_AUTHORITY).
4. Real parent-web clients replacing four hardcoded-throw/`Unavailable*` stubs, each following an already-established client pattern from this session (`RealRequestClient`, `RealRetentionClient`, `RealDeviceEnrollmentClient`).

None of this requires inventing a new authority system. See CLASSIFICATION at the end for the one genuine open question.

## FAMILY_IDENTITY_SOURCE

`families` table (`backend/migrations/0001_mysql_baseline.sql`): `family_id CHAR(36)` primary key, `family_reference_hash` (opaque, hashed reference — never a human-readable name stored server-side), `deleted_at`. This is the only family-identity anchor and it already exists and is populated (referenced by `devices.family_id`, `parent_accounts.family_id`, `enrollment_invitations.family_id`, every `familyId`-scoped route). No new identity table is needed.

## MEMBERSHIP_PERSISTENCE

**Partially exists, genuinely incomplete.** `parent_accounts` (`0013_parent_account_identity.sql`) has a nullable `family_id CHAR(36)` column with **no unique constraint, no foreign key to `families`, and no role column**. `default_parent_member_limit` on the same table proves multi-member-per-family was already anticipated at the billing/capacity layer (it is consumed today by `ParentMemberIncreaseRequest.tsx` / `REQUEST_PARENT_MEMBER_INCREASE`), but the row-level membership/role/invitation-state data was never built.

There is no dedicated `family_members` table and no join table. What a real family/members feature needs, at minimum:
- A `family_member_invitations` table shaped exactly like `enrollment_invitations` (`0016_invitation_lifecycle_states.sql`): `invitation_id`, `family_id`, `invited_email_hash`, `role` (`ADMINISTRATOR` | `VIEWER` — never `OWNER`, see OWNER/ADMIN/VIEWER_AUTHORITY), `status` (`PENDING` → `ACCEPTED` | `EXPIRED` | `REVOKED`), `created_at`, `expires_at`, `invited_by_account_id`. This is a mechanical clone of an already-accepted pattern, not a new design.
- On acceptance, the invited `parent_accounts` row's `family_id` is set (exactly as it presumably already is for the first/owner account today — confirm at implementation time in `ParentAccountService`).
- The DISPLAYED role for a member (`FamilyMember.role` in `parent-web/src/domain/types.ts:196-204`) is NOT read from this table once a member's device is trust-set-active — it is read from the same `TrustSetRoleResolver` used for authorization (see ROLE_RESOLUTION). The invitation/membership table only carries state for the pre-trust-set window (invited, not yet paired a device) and as the record of who invited whom, for audit and for the members list to show a person even before they've paired a device.

## ROLE_RESOLUTION

**Fully exists, already accepted, currently unwired to a real data source.** `backend/src/familyrbac/TrustSetRoleResolver.ts`'s `FamilyTrustSetRoleResolver` resolves `(familyId, deviceId) -> { role, trustSetEpoch, keyEpoch } | ActorResolutionFailure` by reading a `FamilyTrustSetStore.getCurrentEpoch()` and looking up the device's entry. This is real, tested code. Production (`backend/src/main.ts:418`) wires `UnavailableTrustSetRoleResolver` instead, which unconditionally returns `NO_TRUST_SET` — "Explicit production composition boundary while the server-reachable, signature-verified trust-set source is unavailable... Replacing it with the reviewed resolver is a wiring change, not a policy change" (the resolver's own doc comment). No real `FamilyTrustSetStore` implementation beyond `InMemoryFamilyTrustSetStore` (test fixture) exists anywhere in this repository, and no code path populates one from real signed epoch data server-side. This is the actual root gate — the same category of gap as `PRODUCTION_CRYPTO_SUITE`, not a missing design.

**Do not build a second role-resolution mechanism for family/members, screen-time, apps, or audit.** All four must resolve role through this exact same `TrustSetRoleResolver` interface, once wired. Building a parallel "simpler" role check (e.g., reading `parent_accounts.family_id` presence as a proxy for role) would violate doc 18 Section 1 ("Role-based access control is enforced by every receiving endpoint that verifies a signed control envelope; UI hiding is never authorization") and create exactly the kind of divergent, independently-invented authority model this package exists to prevent.

## OWNER/ADMIN/VIEWER_AUTHORITY

Fully specified in `backend/src/familyrbac/policy.ts`'s `OPERATION_MATRIX`, keyed by the existing `ParentOperation` enum (`backend/src/familyrbac/types.ts:25-42`) — doc 18 Section 2's table, already encoded, already unit-tested. Relevant rows, read directly from the matrix:

| Operation | OWNER | ADMINISTRATOR | VIEWER | CHILD |
|---|---|---|---|---|
| `EDIT_CHILD_POLICY` (screen-time + apps writes) | ALLOW | ALLOW | DENY | REQUEST_ONLY |
| `ADD_VIEWER` | ALLOW | ALLOW_IF_CONFIGURED_WITH_STEP_UP | DENY | DENY |
| `REMOVE_NON_OWNER_PARENT` | ALLOW (+ step-up per family config) | configurable | DENY | DENY |
| `ADD_ADMINISTRATOR` | ALLOW_WITH_STEP_UP | DENY | DENY | DENY |
| `CHANGE_ROLE` | ALLOW_WITH_STEP_UP | DENY | DENY | DENY |

`FamilyRbacPolicyConfig` (`administratorCanManageViewers`, `administratorCanRevokeDeviceOrDisableProtection`) is the existing per-family override point for the "configurable" cells — doc 18: "An Owner may choose whether an Administrator can add/remove a Viewer... the safe default is off." This config is itself family policy and must be sourced from the same verified channel as everything else, never a client-asserted flag — it does not yet have a real backing store (currently passed as a `configProvider: () => FamilyRbacPolicyConfig` closure at construction time in every current caller); a real implementation needs this to be readable from durable per-family state, which does not exist yet and is a small, mechanical addition (one row per family, or a column on `families`).

No new operation type is needed for screen-time/apps (`EDIT_CHILD_POLICY` already covers both — see POLICY_WRITE_AUTHORITY on why they are one underlying policy object). Family/members needs no new operations either; `ADD_VIEWER` / `ADD_ADMINISTRATOR` / `REMOVE_NON_OWNER_PARENT` / `CHANGE_ROLE` already exist and are already correctly shaped.

## INVITATION_LIFECYCLE

Two distinct, already-real invitation lifecycles exist in this repo and must not be confused:
- **Device enrollment invitations** (`backend/src/invitation/InvitationService.ts`, `enrollment_invitations` table): an 8-state lifecycle (PCA-ADD-ENR-005) for inviting a *device* to pair into an existing family's trust set. This is fully built, tested, and (per this session's earlier work) has a working real parent-web client (`RealDeviceEnrollmentClient`).
- **Family member invitations** (does not exist yet): inviting a *person* (by email) to become a family member with a given role, independent of any specific device. This is the gap MEMBERSHIP_PERSISTENCE above describes. It should mechanically reuse the enrollment-invitation table's shape (id/family/status/expiry/created-by) and the same rate-limiting/audit conventions already applied to `invitationRoutes.ts`, but it is a genuinely separate table and service because its subject is a person+role, not a device+pairing-key.

A member invitation, once accepted, does not by itself grant trust-set membership — the invited person still has to enroll/pair a device through the existing device-enrollment flow before `TrustSetRoleResolver` can resolve any role for them. The `family_member_invitations` row is what lets the Members UI show "invited, not yet paired" as an honest intermediate state (mirroring `ChildOverview`/`DeviceOfflineNotice`'s existing "state we know, without claiming crypto-verified content" pattern).

## POLICY_WRITE_AUTHORITY

**Screen-time and apps are one underlying policy object, not two.** `android/app/src/main/java/org/pca/app/runtime/schedule/SchedulePolicyEnvelopePayload.kt` defines `SCHEDULE_POLICY_V1`, the real, already-consumed `POLICY_UPDATE` Family Envelope payload: `policyId`, `policyRevision`, `familyId`, `childProfileId`, `timezone`, `windows[]` (each with `daysOfWeek`, `start`/`end`, and an `appScope: All | Apps(appIds)`), `bonusGrants[]`, `parentExceptions[]`, `dailyLimits[]` (each also carrying an `appScope`), `trustSetEpoch`, `keyEpoch`, `issuedAt`, `effectiveFrom`, `expiresAt`. The Android side already encodes/decodes this contract. Parent-web's `ScreenTimePage.tsx` (schedule windows) and `AppsPage.tsx` (per-app allow/deny + daily limits) are two UI facets over subsets of this ONE object's fields, not two backend concepts — `Writer P0-B` owns both together for exactly this reason.

Write authority: `EDIT_CHILD_POLICY`, checked via `ParentActionAuthorizationService` with `targetScope: { kind: 'CHILD_PROFILE', id: childProfileId }` (already-built cross-family denial path — see CROSS_FAMILY_DENIAL). The authorization call is a pre-check only, per `ParentActionAuthorizationService`'s own doc comment: "TRUE authority is the receiving device's own signed-envelope verification against its own trust set, never this service or any server ACL." The actual write is: parent-web constructs a `SCHEDULE_POLICY_V1` payload, encrypts it into a Family Envelope (blocked on `PRODUCTION_CRYPTO_SUITE`), and submits it via the already-real, already-working `POST /v1/runtime-sync/outbound` (`backend/src/http/routes/runtimeSyncRoutes.ts`) — the same relay every other real-but-gated feature this session found (Safe Zone, Retention intake) already uses or would use. **No new backend route is needed for the write path itself.** What's missing, confirmed by `docs/implementation/PCA_COMPLETION_V2_MATRIX.json`'s PCA-10 phase note ("writes (updateScreenTime/updateAppRule) are unimplemented even post-approval"), is the parent-web client code that constructs this envelope — `RealParentFamilyDataGateway.updateScreenTime`/`updateAppRule` are hardcoded throws today and must be replaced with a real implementation, following the `RealSafeZoneClient` pattern (envelope construction + actor-device-session-token requirement), even though it cannot function end-to-end until the crypto gate clears.

## CHILD_BINDING

`ChildProfileMembershipResolver` (`backend/src/childprofiles/ChildProfileMembershipResolver.ts`) is the accepted, already-wired-into-`ParentActionAuthorizationService` interface for verifying a `childProfileId` belongs to the acting family. Its own doc comment is explicit: "this module deliberately does NOT ship a readable central child-profile directory... implementations backed by a trusted endpoint or verified local family state are a later, separate Coordinator binding." There is no `child_profiles` table anywhere in the migrations (`child_profile_id` appears only as a loosely-validated opaque string column on `enrollment_invitations`). Child identity/profile data (name, age, avatar) is family E2EE content, never server-plaintext — consistent with everything else in this architecture. `UnavailableChildProfileMembershipResolver` fails closed (`UNAVAILABLE` → `DENY`) exactly like `UnavailableTrustSetRoleResolver`, and needs the same real, trust-set-backed data source to become real. No new design decision here — reuse the existing interface, wire it once the trust-set source exists.

## DEVICE_BINDING

`devices` table (child device lifecycle: `PAIRING_PENDING` → `PAIRED` → `ACTIVE` → `REVOKED`, `family_id`, `paired_by_account_id`) plus `device_public_keys` (DSK/DEK) plus the trust-set epoch's `FamilyTrustSetEntry.deviceId`. Already real and working (device enrollment, confirmed real-browser-tested this session). No changes needed for this package; screen-time/apps policy targets a `childProfileId`, not a `deviceId`, directly (a child may have zero or more paired devices; the policy envelope is addressed to the child and delivered to whichever of the child's devices is online, per `OutboundRelayService`'s existing fan-out semantics — confirm this at implementation time by reading `OutboundRelayService.ts` fully, not assumed here).

## POLICY_REVISION

`SchedulePolicyV1.policyRevision: Int` (monotonic per child/policy) is the existing contract field. `ParentPolicyRevisionGuard.kt` (Android) is the existing consumer-side guard against applying a stale/out-of-order revision. Backend-side, the closest existing precedent for a monotonic per-target revision counter under concurrent-write protection is the atomic envelope-acceptance transaction referenced in PCA-11's completion-matrix note ("message-id arbitration, replay rejection, **policy-version arbitration** in one MySQL transaction... SOURCE_COMPLETE... backend/test/db/atomicEnvelopeAcceptance.mysql.test.mjs"). Reuse that mechanism; do not build a second one.

## PENDING/DELIVERED/APPLIED_SEMANTICS

Two real, accepted precedents to reuse, not reinvent:
- **Pairing-style** (`backend/src/pairing/PairingService.ts`): `PAIRING_PENDING → PAIRED`, idempotent, never reaches a third "confirmed active" state from this service alone (that's a separate, later lifecycle stage). Used already for device pairing.
- **Removal-decision-style** (`RemovalDecisionAuthority.ts`): `PARENT_APPROVAL_REQUIRED → {KEEP_ACTIVE, TEMPORARILY_DISABLE, ALLOW_REMOVAL}`, durably persisted (migration 0022/0023), three decision *methods* (remote-parent signed / local-PIN / authorized-recovery) collapsing to the same closed state vocabulary, audited via the shared `FamilyAuditService`. This is directly reusable for family/members' "remove a member" or "change a member's role" flows if those are ever made request-and-approve rather than immediate (see IMPLEMENTATION_SEQUENCE for why P0-C should start with immediate OWNER-only mutations and treat approval flows as a later increment, not because the pattern doesn't exist, but to keep the first slice small).
- For screen-time/apps specifically, the relevant three-state model is `PENDING` (envelope submitted, not yet delivered) → `DELIVERED` (`InboundReconnectService` confirms receipt, per its existing receipt/outcome model already used by runtime-sync) → **the frontend must never claim `APPLIED`** — only the child device's own acknowledgement (via its own outbound envelope reporting `lastAcknowledgedPolicyRevision`, already a real field on `FamilyMember`/`ChildOverview`'s `lastAppliedPolicyRevision`) is evidence of actual application. This mirrors the existing, already-enforced rule that `confirmPairing()` can never render `ACTIVE` (defense-in-depth test already exists for this exact anti-pattern in `realDeviceEnrollmentClient.test.ts`).

## IDEMPOTENCY

`ActionIdempotencyLedger` (`backend/src/familyrbac/ActionIdempotencyLedger.ts`) plus `ParentActionAuthorizationService.fingerprintRequest()` (binds an idempotency key to the exact `familyId|actorDeviceId|operation|targetScope` shape, so a reused key against a mutated target never replays a stale decision) is the accepted mechanism, already used by every operation the service authorizes. Screen-time/apps additionally get idempotency for free from `SchedulePolicyV1.policyRevision` plus the atomic envelope-acceptance transaction (see POLICY_REVISION). Family-member invitations should use a fresh UUID `invitation_id` exactly like `enrollment_invitations` already does (`createInvitation`'s `rawInvitationToken`-once-only pattern). No new idempotency primitive needed anywhere in this package.

## REPLAY_PROTECTION

Envelope-level replay protection (`envelope_replay_ledger`, `envelope_message_idempotency_ledger`, `sync_sequence_progress_ledger` tables; PCA-11's "atomic envelope acceptance" mechanism) already exists and is SOURCE_COMPLETE per the completion matrix, currently unreachable only because envelope signature verification is a fail-closed stub. Advisory-authorization-level replay protection is the `ActionIdempotencyLedger` above. Both are reused as-is; no new replay-protection design is needed for any of the four P0s.

## AUDIT_EVENT_MODEL

**This is the one section with a real architectural nuance worth flagging explicitly (see CLASSIFICATION).** `FamilyAuditRecord`/`FamilyAuditService`/`FamilyAuditRepository` (`backend/src/familyrbac/FamilyAuditStore.ts`) is the accepted, already-integrated model (already called from `ParentActionAuthorizationService.recordAudit` and `RemovalDecisionAuthority`). Its own doc comment is unambiguous: "Append-only, **family-local/E2EE store — never a PCA server audit log**, never activity plaintext (doc 18 Section 5/6). Only an in-memory reference implementation exists here; **real persistence is family-device-local storage outside this module's scope**."

`parent-web/src/domain/types.ts`'s `AuditEntrySummary` (eventId, actionType, actorMemberId, targetScope, trustSetEpoch, policyRevision, timestampUtc, resultStatus, reasonCategory, correlationId) already matches `FamilyAuditRecord`'s shape almost field-for-field — the frontend contract was clearly designed against this exact backend type. This strongly implies the intended delivery path for `/security/audit` is the same pattern already built and already localized this session for `ProtectionAlertPanel` (`PENDING_TRUSTED_DECRYPTION` state: audit events are generated server-side as structured records, delivered to the family through the same encrypted outbound/inbound relay as everything else, and decrypted/rendered ONLY on a trusted parent browser) — **not** a new `GET /v1/families/:id/audit-events` endpoint returning plaintext JSON directly from a server-side table. Building the latter would be a straightforward technical shortcut but would contradict this module's own explicit, cited design intent.

`InMemoryFamilyAuditRepository` is a reference implementation only; there is no durable, production `FamilyAuditRepository` anywhere in this codebase today (in-memory means every record is lost on server restart, and — per the doc comment — is not supposed to be durable server-side at all). Building `/security/audit` correctly therefore requires: (a) a durable *transport* record so an audit event survives until delivered (this can reuse the same relay/outbound-envelope tables everything else uses — an audit event becomes just another envelope payload kind, e.g. `AUDIT_EVENT_V1`, encrypted before it ever leaves the server process), and (b) parent-web's `Audit.tsx` rendering decrypted records exactly like `ProtectionAlertPanel` already does, not calling a new plaintext read endpoint.

## SESSION_REQUIREMENTS

Two session models already coexist correctly in this repo and neither should be blurred for this package:
- Parent-web browser session: `RealServiceAuthClient`, HttpOnly cookie, `credentials: 'include'`. Used for account-level operations (login, preferences) and as the transport for the advisory `ParentActionAuthorizationService` pre-check call (which needs `familyId` + the authenticated account's currently-active device identity, not a bearer token).
- Device session: `DeviceSessionService` (challenge/response, `runtime-sync/DeviceSessionService.ts`), a completely different actor (a child device, or — per this session's Dashboard/ChildOverview fix — a browser acting as its own "device" once paired) authenticating to submit/receive envelopes via `requireDeviceSession`.

`ParentActionAuthorizationService.AuthorizeRequest.actorDeviceId` requires the CALLING PARENT BROWSER to itself be a registered trust-set device (this is the "actor-device-session-token ceremony" this session has already named repeatedly as the root external gate for Requests/Safe Zone/Dashboard). Screen-time/apps/members/audit inherit this exact same session requirement — a parent browser must have completed the same not-yet-built browser-side pairing ceremony before any of these four features can authorize anything for real. This is not a new requirement to design; it is the same one already documented and already blocking other features.

## STEP_UP_REQUIREMENTS

Fully specified by `OPERATION_MATRIX` + `requiresStepUp()`/`checkStepUp()` in `ParentActionAuthorizationService`, using `StepUpAssertion` (`FRESH`/`EXPIRED`/`FAILED`/`UNSUPPORTED`/`CANCELLED` states) and `STEP_UP_MAX_FRESHNESS_MS`. `ADD_ADMINISTRATOR` and `CHANGE_ROLE` are `ALLOW_WITH_STEP_UP` for OWNER unconditionally; `ADD_VIEWER`/`REMOVE_NON_OWNER_PARENT` are step-up-required only if the family's `FamilyRbacPolicyConfig` delegates them to an Administrator. `EDIT_CHILD_POLICY` (screen-time/apps) requires no step-up (plain `ALLOW` for OWNER/ADMINISTRATOR) — consistent with it being a routine, frequent parenting action rather than a sensitive one-off. No new step-up design needed; reuse as-is.

## CROSS_FAMILY_DENIAL

Fully built and already the load-bearing IDOR defense for this whole package: `ParentActionAuthorizationService.evaluate()` already cross-checks `DEVICE`/`MEMBER` targets against the SAME verified trust set the actor resolved from, and `CHILD_PROFILE` targets against `ChildProfileMembershipResolver`, collapsing every failure mode (wrong family, unknown, malformed, resolver-unavailable) to the single public `CROSS_FAMILY_TARGET` reason — deliberately, so a caller can never distinguish "exists in another family" from "doesn't exist" (the error-oracle note in `AuthorizationDenyReason`'s doc comment). Family/members' `MEMBER` target scope, screen-time/apps' `CHILD_PROFILE` target scope, and audit's `FAMILY` target scope are all already-modeled `TargetScopeKind` values that flow through this exact same check. No new cross-family defense needs to be designed.

## IMPLEMENTATION_SEQUENCE

**Writer P0-A — FamilyAuthority backend foundation.**
Owns: the `family_member_invitations` migration + repository/service (mechanical clone of `InvitationService.ts`'s pattern, scoped to person+role instead of device+pairing); wiring a real `FamilyRbacPolicyConfig` persistence (one row/column per family, replacing the current closure-injected default); family-scoped negative tests (cross-family target denial, wrong-role denial, expired-action denial) using the *existing* `ParentActionAuthorizationService` test harness patterns already used for `RemovalDecisionAuthority`/`childRequestRoutes.ts` — do not write a new test harness. P0-A does **not** own or attempt to wire a real `TrustSetRoleResolver`/`FamilyTrustSetStore` — that is the same crypto/trust-distribution gate blocking everything else in this program and is explicitly out of scope for a "close these four P0s" pass (see CLASSIFICATION). P0-A's real deliverable is: every new route in P0-B/C/D can call `ParentActionAuthorizationService` today, gets a correct, honest `DENY: ACTOR_NOT_RESOLVABLE` while the resolver is `Unavailable*`, and will start working with zero further backend changes the moment a real resolver is wired in.

**Writer P0-B — Screen Time + Apps policy API.** Depends on P0-A only for the `FamilyRbacPolicyConfig` plumbing (not blocking — can stub the same default P0-A will later back). Builds: the real parent-web client replacing `RealParentFamilyDataGateway.updateScreenTime`/`updateAppRule`'s hardcoded throws, constructing `SCHEDULE_POLICY_V1` envelopes and submitting via the existing `POST /v1/runtime-sync/outbound`; a thin new backend authorization call site (`EDIT_CHILD_POLICY` against `CHILD_PROFILE` target) sitting in front of that submission, mirroring `childRequestRoutes.ts`'s existing call site shape exactly; honest `PENDING`/`DELIVERED`-only UI states (never `APPLIED` without `lastAcknowledgedPolicyRevision` proof); idempotency via `policyRevision`; audit via the existing `FamilyAuditService.record()` call already threaded through `ParentActionAuthorizationService`. No new DB table.

**Writer P0-C — Family Members UI.** Depends on P0-A's invitation table/service. Builds: the real parent-web client (replacing `Members.tsx`'s current demo-only shape and `UnavailableFamilyAuthorityGateway`) for invite (`ADD_VIEWER`/`ADD_ADMINISTRATOR`), list (invitations + trust-set-resolved active members, honestly distinguishing "invited, not yet paired" from "active member with N devices"), remove (`REMOVE_NON_OWNER_PARENT`), change role (`CHANGE_ROLE`); capacity constraints against the existing `default_parent_member_limit`/entitlement system (already real, already used by `ParentMemberIncreaseRequest.tsx`); success/failure feedback following this session's now-established convention (no silent catches). Start with immediate OWNER-only mutations; do not build a `RemovalDecisionAuthority`-style multi-party-approval flow for member removal in this first slice unless a normative requirement explicitly demands it (grep the completion matrix / doc 18 at implementation time — not confirmed in this investigation).

**Writer P0-D — Parent Audit.** Depends on P0-A/B's audit events actually being recorded (they already are, via `FamilyAuditService`, for every operation P0-B/C's new routes authorize). Builds: the encrypted-delivery path (an `AUDIT_EVENT_V1`-shaped envelope, or equivalent, submitted through the existing relay — do not build a plaintext read endpoint, see AUDIT_EVENT_MODEL) and `Audit.tsx`'s real rendering of decrypted `AuditEntrySummary` records with human-readable action-type/target-scope labels (the exact anti-pattern already flagged and fixed once this session, in `ProtectionAlertPanel`'s raw-enum-dump, must not recur here); family-scoped only, zero shared code path with Platform Admin's own (separate, already-real) audit system; pagination/filtering only over what's actually locally decrypted (this is local-content filtering, not a server-side query — another reason this cannot be a simple server read endpoint).

No more than two of P0-B/P0-C/P0-D should run simultaneously per the coordinator's own instruction, and their backend ownership is in fact disjoint as designed above (P0-B touches only runtime-sync submission + one new authorization call site; P0-C touches only the new invitation table + member-management routes; P0-D touches only audit-event envelope delivery) — they do not need to serialize on shared files once P0-A lands.

## CLASSIFICATION

**Mostly `ARCHITECTURE_REUSES_EXISTING_ACCEPTED_MODEL`, with one narrow `NEW_OWNER_DECISION_REQUIRED` sub-question.**

Everything answered above — role resolution, the full OWNER/ADMIN/VIEWER operation matrix, cross-family denial, step-up, idempotency, replay protection, the screen-time/apps wire contract, the pairing-style and removal-decision-style PENDING/DELIVERED/APPLIED precedents — already exists as real, tested, already-partially-wired code (`ParentActionAuthorizationService`, `TrustSetRoleResolver`, `RemovalDecisionAuthority`, `SchedulePolicyEnvelopePayload`, `ActionIdempotencyLedger`, the envelope-acceptance transaction). The only genuinely new work is mechanical: one new migration table (family-member invitations, cloned from the existing invitation-lifecycle pattern), a handful of new HTTP routes that call the existing authorization service with existing operations, and real parent-web clients replacing hardcoded stubs. None of that requires an owner decision — it is the same class of "wire it up following the established pattern" work already done this session for Requests, ProtectionAdministrationPanel, and the billing/retention clients.

The one place a genuine, not-yet-made decision exists: **the audit event model's server-persistence boundary.** `FamilyAuditStore.ts`'s doc comment blanket-states the entire audit trail is "family-local/E2EE... never a PCA server audit log," but the type itself includes several event categories (`STEP_UP_SUCCESS`, `DENIED_AUTHORIZATION_ATTEMPT`, `ROLE_INVITATION`, `DEVICE_LIFECYCLE_TRANSITION`) that do not obviously carry family *activity content* the way, say, a screen-time or location event would — doc 18 Section 5/6 is cited as the source of this rule, but this investigation did not have access to doc 18's full text to confirm whether it draws that same content/metadata line or genuinely requires E2EE for every event category without exception. Recommendation: treat the existing code's blanket instruction as binding (E2EE-only, no server-side plaintext audit log, no new plaintext read endpoint) unless a human explicitly reviews doc 18 Section 5/6 and says otherwise — do not let an implementation writer unilaterally decide this boundary is "probably fine to relax" for convenience. This is the one point where the coordinator should either confirm the safe-default reading above before P0-D starts, or explicitly sign off on relaxing it for the specific non-content event categories.
